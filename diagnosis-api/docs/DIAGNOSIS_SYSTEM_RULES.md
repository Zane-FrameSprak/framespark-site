# 帧火花剧本诊断系统开发规范

本文档用于约束后续 Claude Code 和 Codex 交替开发时保持一致。新 AI 接手诊断系统相关任务时，应先阅读本文档，再阅读当前核心代码。

## 1. 系统定位

帧火花剧本诊断系统是官网中的免费诊断与项目筛选入口。它的第一目标不是替代编剧顾问，而是让用户快速获得一份有依据、有方向的初步判断，同时帮助帧火花识别更值得继续沟通的项目。

大模型只是文本分析引擎。系统的诊断边界、材料类型、报告结构、输出口径和流程控制，必须由本地代码和 prompt 体系共同约束，不能完全交给模型自由发挥。

当前阶段只完成了基础诊断和进阶诊断。终极诊断尚未接入，任何代码、prompt 或前端文案都不应暗示系统已经具备终极诊断能力。

## 2. 诊断阶段边界

第零层：材料准入

材料准入由本地代码完成，负责文件解析、空内容判断、字数范围判断、材料类型归一化等。它不做创作判断，只决定材料是否进入 AI 诊断流程。

基础诊断：判断“这是不是一个故事”

基础诊断关注主角、目标、冲突、情节骨架、人物动机、故事内核等基础要素。它只判断材料是否具备故事基础，不能深入展开人物弧线、类型完成度、制作可行性或市场价值。

进阶诊断：判断“这个故事/材料是否真正成立”

进阶诊断只在基础诊断认为材料可以继续深化时触发。它根据材料类型进一步判断短片表达完成度、长片结构推进力，或其他创意材料的开发潜力。进阶诊断可以比基础诊断更深入，但仍不是终极项目评估。

终极诊断：未开发

终极诊断未来才用于判断项目成熟度、制作可行性、投递价值、平台适配、开发优先级等。当前系统不得正式裁定这些内容。

## 3. 材料类型

当前系统只支持三类材料类型：

- `short`：短片剧本
- `feature`：长片剧本 / 网络电影
- `other`：大纲 / 梗概 / 故事概念 / 人物小传 / 世界观设定 / 片段文本等

如果前端或调用方传入未知类型，后端当前会归一化为 `other`。

## 4. 报告统一 JSON 字段

所有诊断报告必须严格包含以下六个字段：

- `summary`
- `core`
- `strengths`
- `problems`
- `suggestions`
- `nextStep`

其中 `strengths`、`problems`、`suggestions` 必须是数组。模型返回字符串时，parser 可以做兼容转换；但 prompt 和测试仍应坚持数组格式。

不要随意新增报告字段作为前端依赖。确需扩展时，应先明确兼容策略，并同步 parser、测试和前端展示。

## 5. nextStep 前缀规范

`nextStep` 必须以受控前缀开头。当前 parser 为了兼容基础诊断和进阶诊断，在同一 `materialType` 下允许基础与进阶前缀的并集。

基础诊断前缀：

- `建议继续打磨`：材料已有故事基础，但仍有可修改的问题。
- `需要大改`：材料已有一定雏形，但主角、目标、冲突、走向等基础问题较严重。
- `可进入进阶诊断`：材料具备继续深化判断的基础。当前 pipeline 只根据这个前缀触发进阶诊断。
- `建议补充材料`：主要用于 `other`，表示材料与影视创意相关，但信息量不足，需要补充人物、事件、冲突或走向。
- `不适合按长片诊断`：用于 `feature`，表示材料不适合作为长片剧本/网络电影进行基础诊断。
- `不适合按创意材料诊断`：用于 `other`，表示材料与剧本、故事或影视创意无关。

进阶诊断前缀：

- `建议继续打磨`：方向成立，但存在具体可修改的问题。
- `需要结构性重写`：材料具备故事基础，但核心表达、主线结构或执行路径存在结构性问题。
- `可进入下一阶段评估`：进阶层判断基本成立，可以进入未来更高层级的项目评估。
- `暂不适合继续深化`：异常兜底，表示材料被错误送入进阶诊断，或基础条件仍明显不足。
- `需要重新开发`：主要用于 `other`，表示创意核心、人物、冲突、走向之间存在根本性断裂。
- `建议补充材料`：主要用于 `other`，表示创意方向不一定错误，但当前信息不足以继续深化。

注意：不要为了避免 warning 随意创造同义前缀。需要新增前缀时，必须同步 prompt、parser、测试和本文档。

## 6. 用户展示原则

前端当前只展示 `finalReport`。如果基础诊断未触发进阶诊断，`finalReport` 就是基础报告；如果触发进阶诊断，`finalReport` 就是进阶报告。

不要直接向普通用户强调“基础 / 进阶 / 终极”这些后台层级。对用户展示时应使用更友好的诊断类型，例如：

- 故事基础诊断
- 剧本深化诊断
- 创意材料诊断

`internalStage` 只作为后台字段，用于调试、测试和后续产品逻辑，不应成为面向用户的核心文案。

## 7. 语气风格

诊断语气应保持专业、直接、具体、有依据。

必须做到：

- 不无脑夸奖。
- 不毒舌。
- 不输出营销式判断。
- 不为了显得专业而过度批评。
- 不在材料不足时脑补内容。
- 优点和问题都应尽量引用具体情节、角色、场景、设定或人物行为作为依据。
- 每个关键问题必须配修改方向，并说明为什么这样改。

## 8. 项目落地风险原则

基础诊断不判断市场价值、制作难度、演员适配、投资潜力或平台投递价值。

进阶诊断只可以轻量提示后续项目评估风险，例如大规模场景、强演员依赖、类型定位不清、落地方式需要收束等。风险提示不得取代故事判断。

进阶诊断不得正式裁定：

- 拍不出来
- 没人投
- 没有市场
- 不适合投递

终极诊断未来才正式处理制作可行性和投递价值。

## 9. 测试规则

JSON 解析失败、关键字段缺失、接口错误、文件解析失败，应视为 hard failure。

`nextStep` 边界差异、AI 对边界样本的判断不完全一致、同义词未命中、预期阶段和实际阶段存在合理差异，可以作为 soft warning，但必须记录清楚。

E2E 测试验证的是流程：基础诊断、自动分流、进阶诊断、报告结构和错误处理。E2E 测试不等同于真实剧本质量评估，也不能仅凭少量样本断定 prompt 质量已经稳定。

修改相关代码后，应根据范围运行对应测试：

- parser 或报告结构：运行语法检查和 parser 覆盖测试。
- prompt 修改：运行对应 prompt 测试。
- pipeline 修改：运行 E2E dry-run；需要真实验证时再运行 AI E2E。
- 上传、解析、接口修改：补充 HTTP 或端到端链路验证。

新 AI 接手诊断系统相关任务时，先读本文档和当前核心文件：

- `diagnosis-api/src/services/diagnosisPipeline.js`
- `diagnosis-api/src/services/reportParser.js`
- `diagnosis-api/src/services/aiClient.js`
- `diagnosis-api/src/routes/diagnosis.js`
- `diagnosis-api/src/prompts/basicDiagnosis.js`
- `diagnosis-api/src/prompts/advancedShortDiagnosis.js`
- `diagnosis-api/src/prompts/advancedFeatureDiagnosis.js`
- `diagnosis-api/src/prompts/advancedOtherDiagnosis.js`
- `diagnosis-api/scripts/test-e2e-pipeline.js`

接手后应先汇报理解，不要立刻改代码。修改前说明本次边界：改哪些文件、不改哪些文件、是否影响 prompt、pipeline、前端或接口。修改后运行对应测试，并汇报测试结果。

提交前必须确认 `git status`。只提交本次任务相关文件，不混入其他 AI 或用户的未提交改动。未经明确要求，不要 commit，不要 push。
