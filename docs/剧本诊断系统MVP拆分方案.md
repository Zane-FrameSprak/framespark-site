# 剧本诊断系统 MVP 拆分方案

更新时间：2026-05-16

## 前提

本文档用于拆分帧火花剧本诊断系统的第一版开发范围。

当前项目推进以 GitHub 仓库为准。历史文件 `帧火花 剧本诊断系统 设计文档 v2.docx` 作为产品参考，但不直接等同于第一版全部开发范围。

## 总体判断

剧本诊断系统不应一次性做完整版本。完整版本会同时涉及文件上传、文本解析、AI 诊断、内容合规、版权声明、账号系统、报告保存、Word/PDF 下载、频率限制和后端安全，风险和工作量都较高。

第一版应优先跑通最小闭环：

```text
用户上传文本材料
→ 后端读取并校验文本
→ 调用 AI 生成基础诊断报告
→ 前端展示报告
→ 原始文件不长期留存
```

## 第一阶段：最小可用 MVP

目标：验证系统能不能稳定完成一次剧本诊断。

### 第一版做什么

- 新建独立后端服务。
- 前端提供一个简单上传页。
- 支持 `.txt` 和 `.docx`。
- 限制文件大小，例如 10MB。
- 后端解析文件为纯文本。
- 后端做基础守门：
  - 空文件打回
  - 字数太少打回
  - 超出上限时拒绝或提示拆分
- 后端调用 AI 接口生成基础诊断报告。
- 前端展示诊断结果。
- 原始上传文件仅用于本次解析，不长期保存。

### 第一版不做什么

- 不做手机号登录。
- 不做邮箱登录。
- 不做历史报告库。
- 不做 Word/PDF 下载。
- 不做多轮链式深度诊断。
- 不做完整内容合规系统。
- 不做短信验证码。
- 不做人才平台联动。
- 不做后台管理系统。

这些能力后续分阶段补充。

## 推荐技术结构

当前官网仍保持静态站点。

剧本诊断系统建议新建后端服务：

```text
framespark-site/              # 当前静态官网
framespark-diagnosis-api/     # 后续可单独新建的后端服务
```

后端建议：

- Node.js
- Express 或 Fastify
- `multer` 处理上传
- `mammoth` 解析 `.docx`
- `.txt` 直接读取
- DeepSeek / OpenAI 兼容接口用于诊断

第一阶段不建议把 API Key 写进前端。AI API Key 必须只存在后端环境变量中。

## 第一版接口设计

### `POST /api/diagnosis`

用途：上传材料并生成基础诊断报告。

请求：

```text
multipart/form-data
file: .txt 或 .docx
materialType: simple | full
```

响应成功：

```json
{
  "ok": true,
  "report": {
    "summary": "一句话判断",
    "strengths": ["亮点 1", "亮点 2"],
    "problems": ["问题 1", "问题 2"],
    "suggestions": ["建议 1", "建议 2"],
    "nextStep": "建议继续打磨 / 需要大改 / 可进入下一阶段"
  }
}
```

响应失败：

```json
{
  "ok": false,
  "error": {
    "code": "FILE_TOO_SHORT",
    "message": "可展示给用户的错误说明"
  }
}
```

## 基础错误码

- `UNSUPPORTED_FILE_TYPE`：不支持的文件格式
- `FILE_TOO_LARGE`：文件过大
- `FILE_EMPTY`：文件为空
- `FILE_PARSE_FAILED`：文件解析失败
- `FILE_TOO_SHORT`：字数太少，无法诊断
- `FILE_TOO_LONG`：文本过长，第一版暂不支持
- `AI_REQUEST_FAILED`：AI 诊断失败

## 第一版诊断报告结构

第一版不要追求完整七维度深度报告，先采用基础结构：

1. 一句话判断
2. 故事核心是否清晰
3. 主要亮点
4. 主要问题
5. 修改建议
6. 下一步判断

报告语气要求：

- 客观
- 具体
- 不打分
- 不无脑夸奖
- 不无脑否定
- 能说明“为什么这样建议”

## 后续阶段拆分

### 第二阶段：可信与安全

- 上传前用户声明勾选
- 基础频率限制
- 临时文件删除机制明确化
- 操作日志
- 更完善的错误提示
- 内容合规初筛

### 第三阶段：专业诊断体系

- 快速诊断
- 进阶诊断
- 深度诊断
- 七维度报告
- 多轮链式调用
- 具体场次引用
- 自动生成或优化故事梗概

这一阶段更适合先让 Claude Code / Claude 帮忙打磨评估标准、维度定义和提示词，再由 Codex 落代码。

### 第四阶段：产品化

- 手机号登录
- 邮箱登录
- 报告历史记录
- Word/PDF 下载
- 用户授权数据留存
- 后台管理
- 与人才平台联动

## 当前建议下一步

1. 先确认第一版是否只支持 `.txt` 和 `.docx`。
2. 确认第一版是否需要账号登录；建议暂不需要。
3. 确认 AI 服务提供方和模型名。
4. 新建后端服务骨架。
5. 做一个最小上传诊断接口。
6. 再把官网 `diagnosis/` 入口页改成真实上传页。
