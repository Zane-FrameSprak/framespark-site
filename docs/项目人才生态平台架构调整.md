# 项目人才生态平台架构调整

本文档用于定义项目人才生态平台的产品方向、信息架构和长期模块边界，不代表所有功能需要一次性开发。正式开发时应按 MVP 优先级拆分实施，并根据实际业务验证结果持续调整。

## 当前战略结论

项目人才生态平台不是商业撮合平台，而是 FrameSpark 生态的基础设施。

它服务于 FrameSpark “稳定量产优质影视项目” 的长期目标。

短期内，它主要是：

- FrameSpark 自身调度人才的内部工具
- 对外展示创作者与行业人才的品牌窗口
- 人才被看见、被联系、被记录的基础档案库

平台长期免费，不以商业化为第一目标，不追求规模化，不与现有商业人才平台正面竞争。

第一阶段产品形态是“人才档案库”，不是项目撮合平台、普通招聘平台或 ProjectDemand 匹配工作台。

## 一、背景

帧火花官网目前有三个主要入口：

- 故事开发诊断系统
- 项目人才生态平台
- 帧火花开发中项目

原人才平台更偏人才库，主要围绕人才档案、职业信息和合作记录展开。当前阶段战略重新收束：项目人才生态平台第一阶段不做商业撮合、不做项目发布、不做 ProjectDemand 招募需求，不做复杂匹配工作台，而是先建立 FrameSpark 生态的人才档案库、内部人才调度基础设施和对外品牌窗口。

## 二、新定位

名称暂定：

帧火花项目人才生态平台

对外可使用：

- 项目人才专区
- 项目招募专区

一句话定位：

让创作者与影视行业人才被看见、被联系、被记录，为 FrameSpark 长期稳定调度人才和推进项目生产建立基础。

第一阶段核心不是“项目找人、人找项目”的撮合交易，而是人才档案库：

- 平台第一阶段不发布项目。
- 项目方 / 制片 / 剧组不需要填写项目资料和招募需求。
- 平台核心是让人才被看见，让找人的人能找到。
- 制片或项目相关人员可以搜索人才、查看档案、发起联系。
- 沟通转移到平台外完成，例如微信、电话、线下沟通等。
- 平台只承担“促成双方见面”的职能，不承担项目质量、合作执行和合作纠纷责任。

## 架构层关键决策

### 完整架构，分阶段开放

项目人才生态平台不是临时简陋 MVP，也不是一次性开发所有功能。

第一版上线时，底层架构要尽量完整，至少要预留用户、项目方实体、人才档案、作品贡献、合作记录、联系请求、收藏、通知、审核状态、行为日志和可信记录等核心对象。外显功能可以分阶段开放，但数据模型和权限边界不能从一开始就做成无法扩展的简单名片页。

第一版目标是“完整架构下的人才档案库核心闭环”：先跑通注册登录、档案创建、作品上传、人才搜索、联系请求和基础审核，再逐步开放收藏、通知、小程序、背书和合作记录。Project 与 ProjectDemand 保留结构，但第一阶段不进入用户侧主流程。

### Web 核心闭环优先，小程序后置

当前阶段优先设计和开发 Web 端核心闭环。小程序第一阶段不开发。

不要把“静态原型”或“微信登录打通方案”写成第一阶段目标。静态原型只用于说明产品结构，不是正式系统闭环。微信登录打通属于账号体系架构，不是轻量功能，后续需要单独设计。

Web 第一阶段应优先处理注册登录、人才档案完整创建、作品集上传、档案深度编辑、多维度搜索、联系请求管理和后台审核。只有 Web 端人才档案库核心闭环稳定后，再设计小程序轻量入口。

### Web 是工作台，小程序未来是入口和状态机

Web 适合：

- 复杂资料填写
- 人才档案完整创建
- 作品与履历上传
- 多维度搜索与筛选
- 联系请求管理
- 审核后台
- 运营治理

小程序未来适合：

- 浏览项目机会
- 浏览人才名片
- 收藏
- 快速申请
- 接收通知
- 扫码展示个人主页
- 档期状态轻量更新

两端未来必须共用同一套后端和数据模型，不要各做一套数据。Web 和小程序可以有不同交互，但不能有两套用户、两套项目、两套人才档案或两套审核状态。

### 小程序定位：微信场景下的轻入口和状态工具

Web 是项目人才生态平台的主工作台。小程序是微信场景下的轻入口、提醒入口、名片入口和状态更新工具。

小程序不承载故事开发诊断系统。小程序不替代 Web 端工作台。小程序不作为完整项目管理后台。

小程序未来适合承担：

- 日常浏览人才档案
- 查看人才主页
- 查看人才公开名片
- 收藏人才
- 接收联系、审核、档期提醒等通知
- 扫码展示个人主页或人才名片
- 快速更新档期状态，例如可合作、档期待定、暂不接、仅远程
- 查看联系和邀请状态

第一版小程序不做：

- 完整项目创建
- ProjectDemand 发布
- 复杂人才档案编辑
- 作品集上传
- 审核后台
- 即时聊天
- 合同
- 支付
- 完整日历
- 复杂筛选和管理后台
- 官方微信群运营

当前第一阶段仍然是 Web 核心闭环优先，小程序后置。小程序第一阶段不进入开发主线。后续再根据 Web 核心闭环和真实用户反馈，设计小程序轻量版本。

### 微信生态与沟通边界

帧火花不以微信群作为官方项目分发和管理渠道。平台不默认建立官方微信群或企业微信群。微信群可以是用户私下沟通工具，但不是帧火花平台的基础设施。

联系请求、邀请确认、档期状态和合作记录必须回到平台内结构化记录。平台外沟通可以发生，但关键节点不能只留在微信群或私聊里。

微信生态只承担：

- 小程序入口
- 分享卡片
- 订阅通知
- 扫码名片

企业微信协作群不作为默认流程。仅在后期高信任人工服务中考虑，例如：

- 帧火花自有项目
- 入选孵化项目
- 付费撮合服务
- 纠纷协调
- 重点项目服务

## 三、三个官网入口的边界

### 故事开发诊断系统

故事材料诊断入口。面向一句话创意、故事概念、梗概、大纲、人物小传、世界观设定、片段文本和完整剧本，帮助用户判断材料当前阶段是否成立，以及下一步应补什么。

### 项目人才生态平台

FrameSpark 生态的人才档案库与品牌窗口。面向影视人才、制片与找人场景、潜在合作方和帧火花运营方，提供人才档案展示、作品履历、搜索筛选、联系请求、合作记录和基础审核。

### 帧火花开发中项目

公司自有项目展示入口。只展示帧火花自有、主控或明确由帧火花参与开发的项目。

帧火花自有项目展示不等于外部项目广场。第一阶段不开放外部项目发布。未来如恢复外部项目展示或招募需求，应进入项目人才生态平台，不应混进“帧火花开发中项目”。

## 四、项目类型分层

项目分层为长期预留，不是第一阶段用户侧主流程。第一阶段不发布项目、不发布 ProjectDemand、不开放项目招募。

长期如恢复项目能力，平台内项目至少分为三层：

- 帧火花自有项目：由帧火花主控、开发或明确参与运营的项目。
- 外部合作项目：外部项目方发布或授权展示的合作需求。
- 入选 / 孵化观察项目：经过初步筛选，进入帧火花观察、孵化或合作洽谈范围的项目。

第一版不使用“帧火花推荐项目”这个名称，因为“推荐”带有强背书意味。后续如果使用，必须建立审核标准，例如项目资料完整度、版权声明、项目方身份、开发阶段、合作需求真实性和帧火花审核记录。

## 五、平台核心用户

- 制片 / 找人方：搜索人才、查看档案、收藏人才、发起联系。
- 影视人才：完善人才档案、展示作品和经历、接收联系或合作邀请。
- 帧火花运营方：审核项目、审核人才、管理平台内容、处理举报或纠纷线索。
- 潜在合作方 / 制片方 / 投资方：浏览项目机会、筛选人才、观察项目成熟度与合作可能性。

## 六、核心对象模型

### User 用户

系统登录主体。用于承载账号、权限、联系方式、安全设置和身份状态。

### UserProfile 用户资料

用户的基础资料层。可包含昵称、头像、联系方式、城市、认证信息和公开展示设置。

### ProductionEntity 项目方实体

项目方实体表示真实发起或管理项目的一方，可以是个人、工作室、公司、剧组或制片团队。

User 可以创建或加入多个 ProductionEntity。Project 应归属于 ProductionEntity，而不是直接只归属于某一个 User。这样后续才能表达一个制片团队、多名成员共同管理项目、不同成员拥有不同权限的情况。

ProductionEntity 是区分“账号”和“项目方主体”的关键对象。没有这一层，平台很容易退化成个人用户随意发布项目，后续也难以处理团队权限、项目归属、公司主体、剧组主体和责任边界。

### TalentProfile 人才档案

影视人才的职业档案。用于展示职业身份、技能标签、作品履历、可合作状态和合作偏好。

### Project 项目

项目本体。用于描述项目名称、类型、阶段、来源、标签、公开简介和审核状态。

第一阶段保留但暂不启用。Project 在数据库设计中保留结构，但不进入用户侧主流程，不进入匹配池，不作为平台核心功能。未来如果恢复项目展示、项目发布、诊断项目推荐或招募需求，可以重新启用。

### ProjectDemand 项目需求 / 招募岗位

项目当前正在寻找的人或合作资源。

第一阶段保留但暂不启用。ProjectDemand 在数据库设计中保留结构，但不进入用户侧主流程，不进入匹配池，不作为平台核心功能。第一阶段不做项目发布、不做招募需求、不做商业撮合。未来如果恢复项目展示、项目发布、诊断项目推荐或招募需求，可以重新启用。

### Work 作品 / 履历

用户参与过的作品或可展示成果。可作为人才档案和申请项目的可信支撑。

### WorkCredit 作品贡献关系

WorkCredit 表示一个作品中的具体贡献关系。

一个 Work 可以有多个 TalentProfile 参与，每个人在作品中有不同角色，例如编剧、导演、摄影、演员、剪辑、制片、美术等。不要只用 Work 直接绑定单一用户，否则后期无法表达多人协作作品，也无法建立真实的作品关系图谱。

WorkCredit 的价值在于把“作品”与“具体贡献”拆开：作品是成果，贡献关系才说明某个人在其中做了什么。

### Application 申请 / 投递

人才对某个项目需求发起的申请记录。

第一阶段可不启用。当前核心交互是 ContactRequest 联系请求，不是对 ProjectDemand 的投递申请。Application 可作为未来恢复项目需求时的预留对象。

### CollaborationRecord 合作记录

CollaborationRecord 表示真实发生过的合作关系，是合作关系图谱的基础。

Endorsement 是评价或背书，CollaborationRecord 是合作事实记录，两者不要混为一谈。平台可以先记录“谁和谁在什么项目中合作过、担任什么角色、合作是否完成”，再在此基础上允许双方或项目方发起背书。

合作记录应尽量避免单方虚构，最好由双方确认或由项目方确认。

### Match 匹配记录

平台、运营方或规则系统产生的人才与项目需求之间的匹配记录。

第一阶段不启用复杂匹配，不以 Match 作为产品核心。保留 Match 是为了未来可能恢复项目需求、诊断项目推荐或内部调度推荐。

### Endorsement 背书 / 合作评价

用于沉淀合作可信度。第一版建议先做合作记录和文字背书，不急着做公开评分。

### ContactRequest 联系请求

找人方与人才之间的轻量联系入口。第一版不做复杂即时聊天，先做联系请求与状态流转。沟通可以转移到平台外完成，平台保留“谁联系了谁、什么时间、基于什么档案发起联系”的结构化记录。

### ReviewStatus 审核状态

用于项目、需求、人才档案、作品、背书等对象的审核状态控制。

### ActionLog 行为日志

从第一天就应预留 ActionLog。

ActionLog 至少记录：谁、什么时间、对什么对象、做了什么动作。它不一定第一版就做复杂分析，但字段和写入位置要从架构层预留。

ActionLog 的长期价值包括：

- 推荐优化
- 风控
- 反作弊
- 平台运营分析
- 审核追溯
- 纠纷处理时的基础证据

## 实体启用策略

### 第一阶段核心启用实体

- User
- ProductionEntity
- TalentProfile
- Work
- WorkCredit
- CollaborationRecord
- Endorsement
- ContactRequest
- Favorite
- Notification
- ReviewStatus
- ActionLog

### 第一阶段保留但暂不启用实体

- Project
- ProjectDemand
- Application
- Match

Project 和 ProjectDemand 在数据库设计中保留结构，但第一阶段不进入用户侧主流程，不进入匹配池，不作为平台核心功能。未来如果恢复项目展示、项目发布、诊断项目推荐或招募需求，可以重新启用。

### 保留的架构判断

- ProductionEntity 作为独立实体，不是 User 直接拥有所有项目或联系场景。
- WorkCredit 作为多对多关联表，用于表达一个作品多人贡献、一个人在不同作品担任不同角色。
- CollaborationRecord 作为合作关系图谱基础，第一阶段可由用户主动声明 + 双方确认产生，不依赖 Project 派生。
- ActionLog 从第一天预留行为日志。
- 所有核心实体使用 UUID，不使用自增 ID。
- 权限按“动作 + 对象”判断，不按固定身份判断。
- 一个 User 可以同时是项目方和人才，身份是场景，不是单一字段。

## 七、Project 项目字段建议

Project 建议字段：

- projectId
- productionEntityId
- projectName
- projectType
- sourceType
- developmentStage
- genreTags
- publicSummary
- coverImage
- city
- remoteAllowed
- visibility
- reviewStatus
- createdBy
- createdAt
- updatedAt

字段说明：

- projectType：短片、长片、剧集、网络电影、纪录片、动画、实验影像等。
- productionEntityId：项目所属的项目方实体。Project 归属于 ProductionEntity，不应只直接归属于 User。
- sourceType：framespark_owned、external、selected_observation 等。
- developmentStage：概念、梗概、大纲、剧本开发、筹备、拍摄、后期、发行等。
- visibility：公开、仅审核可见、仅受邀可见、草稿。
- reviewStatus：pending、approved、rejected、hidden / removed 等。

Project 是项目容器，不是第一阶段启用的用户侧核心对象。它承载项目背景、调性、开发阶段、项目来源、所属项目方、公开简介和审核状态，作为未来恢复项目展示、诊断项目推荐或招募需求时的预留结构。

帧火花自有项目、外部项目、入选 / 孵化观察项目，不应拆成三个独立实体。统一使用 Project 实体，通过 sourceType 字段区分：

- framespark_owned：帧火花自有 / 主控项目
- external：外部项目方发布
- selected_observation：入选 / 孵化观察项目

同时结合 reviewStatus、visibility、ProductionEntity 权限、是否进入首页展示等字段，决定项目展示范围和权限。

外部项目默认不叫“推荐项目”。“推荐 / 入选 / 自有”必须分层，避免平台背书风险。

第一阶段不启用 Project 用户侧发布，不开放项目方填写项目资料。

## 八、ProjectDemand 项目需求字段建议

ProjectDemand 建议字段：

- demandId
- projectId
- roleNeeded
- description
- cooperationType
- budgetRange
- locationRequirement
- availabilityRequirement
- experienceRequirement
- portfolioRequired
- expectedStartDate
- expectedEndDate / expectedDuration
- projectCity
- workMode
- acceptsNonLocalTalent
- providesTravelSupport
- status
- reviewStatus
- createdAt

ProjectDemand 是未来恢复招募需求时的匹配单元，但第一阶段不启用。

如果未来恢复项目发布和招募需求，Project 是项目容器，ProjectDemand 是匹配单元。真正进入匹配池的是 ProjectDemand，不是 Project 本身。

示例：

- “某短片项目”不是匹配单元。
- “某短片 7 月上海寻找摄影指导，驻组 5 天，有偿”才是匹配单元。

ProjectDemand 必须依附于 Project 存在，不能脱离项目单独发布。原因是同一项目下的多个需求需要共享项目背景、调性、阶段、团队与来源信息。

第一阶段不做 ProjectDemand 发布，不做招募需求，不做商业撮合。上述字段仅作为长期架构预留。

字段说明：

- roleNeeded：编剧、导演、制片、摄影、美术、剪辑、演员、宣发、项目顾问等。
- cooperationType：有偿合作、联合开发、项目制、长期合作、志愿 / 低预算、待议。
- budgetRange：可选公开范围，不强制显示具体金额。
- workMode：本地、远程、驻组、混合。
- status：open、paused、filled、closed。
- portfolioRequired：是否需要提交作品集或代表作品。

## 十一、申请与联系

第一版不做复杂即时聊天。优先做轻量申请和联系请求：

- Application：人才对项目需求发起申请，包含申请说明、作品链接、状态和项目方处理记录。
- ContactRequest：用户之间发起联系请求，包含发起人、接收人、关联项目或需求、联系理由和处理状态。

建议状态：

- pending：待处理
- accepted：已接受
- declined：已拒绝
- withdrawn：已撤回
- expired：已过期

这样可以先完成合作连接闭环，同时避免即时聊天、消息安全、骚扰控制和通知系统过早复杂化。

## 十二、背书与合作记录

Endorsement 用于建立平台可信度。

第一版可以先做合作记录和文字背书，不急着做公开评分。原因是评分系统容易带来争议、刷分、报复性评价和平台责任边界问题。

建议第一版包括：

- 合作对象
- 关联项目
- 合作角色
- 合作时间
- 背书文字
- 是否公开
- 是否双方确认
- 审核状态

后续可再扩展为更复杂的信用机制，但应避免在早期承诺平台对合作结果进行强担保。

## 审核机制必须前置

上线时必须有人工审核机制。

第一阶段主要审核对象是：

- TalentProfile
- Work
- WorkCredit
- ProductionEntity
- ContactRequest 中的异常行为

第一阶段不审核项目需求，因为第一阶段不发布项目、不发布 ProjectDemand。

审核状态第一版可以简化为：

- pending：待审核
- approved：已通过
- rejected：已拒绝
- hidden / removed：隐藏或移除

审核重点：

- 身份真实性
- 信息合规性
- 是否明显虚假
- 是否有侵权或不当内容
- 是否存在骚扰或恶意联系

不审核：

- 创作水平高低
- 项目商业价值
- 合作结果

审核不一定第一版就做复杂工作流系统，但 reviewStatus 字段和“未审核不公开展示 / 不进入联系推荐”的规则必须从架构层存在。

## 权限与内容归属

权限不应只按角色判断，而应按“动作 + 对象”判断。

示例：能否编辑某个对象，不是看 User 是否拥有固定“项目方角色”，而是看 User 与该对象的归属关系及具体权限。未来如启用 Project，能否编辑 Project 应看 User 是否属于该 Project 所属的 ProductionEntity，且是否拥有对应权限。

内容归属建议：

- Project 归属于 ProductionEntity。
- ProjectDemand 归属于 Project。
- TalentProfile 归属于 User。
- Work 可由人才上传，也可关联 Project。
- WorkCredit 表示人才在作品中的具体贡献。
- Endorsement 归发出方所有，被背书方不能修改，但可选择隐藏或申诉。
- CollaborationRecord 需要双方或项目方确认，避免单方虚构合作。

权限模型应支持一个 User 同时拥有多个身份和多个组织关系，而不是只用一个 role 字段决定所有行为。

## 档期与地域协作

第一阶段不做复杂匹配算法，但人才档期和地域协作方式仍然是人才档案库的重要字段。它们用于帮助找人的人快速判断是否值得发起联系，也为 FrameSpark 内部调度人才提供基础。

人才端建议字段：

- availabilityStatus
- availabilityBlocks
- baseCity
- availableCities
- acceptsRemote
- acceptsTravel
- acceptsOnsite
- maxTravelDays
- travelRequirement
- lastAvailabilityUpdatedAt

未来如恢复 ProjectDemand，项目需求端建议字段：

- expectedStartDate
- expectedEndDate / expectedDuration
- projectCity
- workMode：本地 / 远程 / 驻组 / 混合
- acceptsNonLocalTalent
- providesTravelSupport

未来基础匹配规则：

- 项目必须本地 + 人才不在本地且不接受异地 = 不匹配。
- 项目可远程 + 人才接受远程 = 可匹配。
- 项目需驻组 + 人才接受异地且档期覆盖 = 可匹配。
- 项目周期与人才不可合作区间冲突 = 不推荐或降权。
- 档期长期未更新 = 标记档期待确认。

这些规则是长期预留。第一阶段不做复杂匹配，但不能忽略档期、城市、远程、驻组和差旅条件这些基础信息。

## 推荐原因标签

第一版不做复杂 AI 推荐算法。

第一版的推荐原因应来自硬条件和基础软条件的命中项展示。用标签解释“为什么推荐”，比一个不透明分数更可信。

示例标签：

- 工种对应
- 档期可用
- 城市匹配
- 可远程
- 可驻组
- 合作方式匹配
- 作品类型接近
- 档期待确认
- 报酬需确认

不要在第一版使用不透明的“匹配度 92%”作为主要表达。第一阶段如出现人才列表排序或推荐位，应使用可解释标签，而不是商业撮合式分数。

## 身份视角

一个 User 可以同时是人才、项目方、创作者、ProductionEntity 成员。

身份不是单一字段，而是场景和动作。前端可以提供当前视角：

- 人才视角：维护自己的档案、作品、档期和联系状态。
- 找人视角：搜索人才、查看档案、收藏人才、发起联系。
- 运营视角：审核和治理。

推荐人才不应作为所有用户的默认模块。只有找人视角或 FrameSpark 内部调度场景才展示推荐人才。

这一点非常重要：第一阶段平台本质是人才档案库和内部调度基础设施，不是默认向所有人展示“推荐人才”的撮合市场。

## 十六、官网版与小程序版分工

当前阶段优先设计和开发 Web 端核心闭环。小程序第一阶段不开发。

官网 Web 版适合：

- 注册登录
- 完善详细档案
- 上传作品集
- 作品集上传
- 档案深度编辑
- 多维度搜索和筛选
- 联系请求管理
- 基础审核后台

小程序版适合：

- 微信登录，并与 Web 账号打通
- 日常浏览人才档案
- 查看人才主页，只读为主
- 收藏
- 通知接收和响应
- 扫码展示个人主页或人才名片
- 快速更新档期状态，例如可合作、档期待定、暂不接、仅远程
- 发起联系请求

小程序第一版不适合承担：

- 完整项目创建
- ProjectDemand 发布
- 复杂人才档案编辑
- 作品集上传
- 审核后台
- 即时聊天
- 合同
- 支付
- 项目发布
- ProjectDemand 发布
- 完整日历
- 复杂筛选和管理后台
- 官方微信群运营

两端必须共用同一套后端，不要各做一套数据。Web 和小程序可以有不同界面，但对象模型、审核状态、用户权限和项目需求数据应保持一致。

Web 是工作台，小程序未来是入口和状态机。微信登录打通属于账号体系架构，不是轻量功能，后续应单独设计。

用户在 Web 更新档案、项目、申请、收藏、档期，小程序应同步显示。用户在小程序收藏、申请、更新档期，Web 端也应同步显示。小程序只暴露轻量操作，不维护独立数据。

## 十七、与故事开发诊断系统的关系

两者互相导流，但不混成一个系统。

诊断系统可以在报告底部引导用户进入项目人才生态平台完善人才档案、展示作品或寻找潜在合作方，例如：

- 完善人才档案
- 展示代表作品
- 寻找编剧顾问
- 寻找导演或制片合作

但第一版不要自动把用户材料公开到项目人才平台。故事材料、诊断报告或项目信息进入项目人才生态平台，必须由用户主动选择，并经过审核。

调整后的关系是“软连接，不是强漏斗”：

- 故事开发诊断系统所有人都能用，免费。
- 人才平台所有人都能进入注册，免费。
- 诊断系统内部基础 / 进阶 / 终极阶段用户不感知。
- 当用户提交的材料通过终极诊断时，可以询问用户是否愿意将作品推荐到人才平台未来的展示项目中。
- 用户必须主动选择，不自动公开材料。
- 未通过诊断的项目或用户仍可自由使用人才平台，不受影响。

## 十八、与帧火花自有项目展示的关系

首页“帧火花开发中项目”只展示公司自有或主控项目。

第一阶段不开放外部项目发布。未来如果恢复外部项目展示，应进入项目人才生态平台，而不是进入“帧火花开发中项目”。

不要混淆：

- 自有项目
- 外部项目
- 入选 / 孵化观察项目

这三类项目的展示位置、标识、审核标准和平台背书强度都应不同。

## 二十、风险与边界

主要风险：

- 外部项目真实性风险
- 版权归属风险
- 人才资料造假
- 平台背书边界不清
- 恶意联系或骚扰
- 合作纠纷外溢到平台
- 人才库冷启动风险

应对原则：

- 人才资料和作品需要审核
- 平台只提供展示、联系和记录，不直接保证合作结果
- 推荐 / 入选 / 自有项目要分层

平台文案应避免过度承诺。尤其是“推荐”“认证”“背书”“入选”等词，需要有明确规则支撑后再使用。

### 冷启动风险

人才档案库最大的风险是冷启动。

如果没有足够可信、可展示的人才档案，找人的人会离开；如果没有真实联系机会，人才也不会持续维护资料。上线前必须准备种子 TalentProfile、种子作品资料、种子 ProductionEntity 和 FrameSpark 内部可用的人才调度场景。

信用机制依赖真实合作记录。冷启动期 CollaborationRecord 和 Endorsement 会很少，因此第一版不能过度依赖信用分。早期更重要的是：

- 资料完整度
- 审核状态
- 作品资料
- 档期和协作方式是否清楚
- 联系请求是否真实、克制、可追溯

## 二十一、后续推进顺序

建议推进顺序：

2. 第二阶段：设计 Web 端人才档案库核心闭环
3. 第三阶段：设计 User / ProductionEntity / TalentProfile / WorkCredit 数据模型
4. 第四阶段：设计 Web 版人才档案、作品上传、搜索筛选、联系请求和审核后台页面

8. 第八阶段：后期再设计小程序、微信登录打通、复杂推荐、信用分和 Project / ProjectDemand

每一阶段都应围绕核心闭环验证推进，不应把长期愿景直接当成一次性开发清单。

## 当前 talent 静态页的改造方向

当前 talent 页面不应继续做成项目撮合展示页或匹配工作台。

## 通知机制原则

通知追求时效性，不追求高频打扰。

微信订阅消息未来用于核心通知：

- 被联系
- 被合作邀请
- 档期临期
- 审核结果

非核心信息走站内消息。

通知触发必须走异步队列，不阻塞用户操作。

重要通知设计多通道备份：微信订阅消息 + 站内消息。

通知优先级分级：

- 即时
- 当日
- 不推送
