# 项目人才生态平台架构调整

本文档用于定义项目人才生态平台的产品方向、信息架构和长期模块边界，不代表所有功能需要一次性开发。正式开发时应按 MVP 优先级拆分实施，并根据实际业务验证结果持续调整。

## 一、背景

帧火花官网目前有三个主要入口：

- 故事开发诊断系统
- 项目人才生态平台
- 帧火花开发中项目

原人才平台更偏人才库，主要围绕人才档案、职业信息和合作记录展开。随着官网产品方向扩展，平台需要升级为“项目 + 人才 + 合作需求”的综合生态平台，既能让项目方发布需求，也能让人才展示能力、寻找项目机会，并为后续合作记录、背书机制和项目孵化提供基础。

## 二、新定位

名称暂定：

帧火花项目人才生态平台

对外可使用：

- 项目人才专区
- 项目招募专区

一句话定位：

项目找人，人找项目，平台提供展示、筛选、连接和基础可信机制。

平台不是单纯人才库，也不是公开项目广场，而是围绕影视项目合作建立的连接入口。第一版应优先解决“谁在找人”“谁能参与”“如何可信地发起联系”这三个问题。

## 架构层关键决策

### 完整架构，分阶段开放

项目人才生态平台不是临时简陋 MVP，也不是一次性开发所有功能。

第一版上线时，底层架构要尽量完整，至少要预留项目、项目需求、人才档案、作品贡献、档期、申请、联系、审核、行为日志和可信记录等核心对象。外显功能可以分阶段开放，但数据模型和权限边界不能从一开始就做成单一人才库或普通招聘页面。

第一版的目标应是“完整架构下的核心闭环版本”：先跑通项目需求与人才档案之间的发布、筛选、申请、联系和审核闭环，再逐步开放匹配、背书、通知、小程序和更复杂的信用体系。

### Web 核心闭环优先，小程序后置

当前阶段优先设计和开发 Web 端核心闭环。小程序第一阶段不开发。

不要把“静态原型”或“微信登录打通方案”写成第一阶段目标。静态原型只用于说明产品结构，不是正式系统闭环。微信登录打通属于账号体系架构，不是轻量功能，后续需要单独设计。

Web 第一阶段应优先处理复杂资料、项目创建、需求发布、作品上传、申请管理、审核后台和项目方筛选人才。只有 Web 端核心对象和流程稳定后，再设计小程序入口。

### Web 是工作台，小程序未来是入口和状态机

Web 适合：

- 复杂资料填写
- 项目创建与管理
- 项目需求发布
- 作品与履历上传
- 申请与联系管理
- 人才筛选
- 审核后台
- 运营治理

小程序未来适合：

- 浏览项目机会
- 浏览人才名片
- 收藏
- 快速申请
- 接收通知
- 扫码展示个人主页
- 档期状态轻量更新

两端未来必须共用同一套后端和数据模型，不要各做一套数据。Web 和小程序可以有不同交互，但不能有两套用户、两套项目、两套人才档案或两套审核状态。

## 三、三个官网入口的边界

### 故事开发诊断系统

故事材料诊断入口。面向一句话创意、故事概念、梗概、大纲、人物小传、世界观设定、片段文本和完整剧本，帮助用户判断材料当前阶段是否成立，以及下一步应补什么。

### 项目人才生态平台

项目与人才连接入口。面向项目方、影视人才、潜在合作方和帧火花运营方，提供项目需求发布、人才档案展示、申请参与、联系请求、合作记录和基础审核。

### 帧火花开发中项目

公司自有项目展示入口。只展示帧火花自有、主控或明确由帧火花参与开发的项目。

帧火花自有项目展示不等于外部项目广场。外部项目应进入项目人才生态平台，不应混进“帧火花开发中项目”。

## 四、项目类型分层

平台内项目至少分为三层：

- 帧火花自有项目：由帧火花主控、开发或明确参与运营的项目。
- 外部合作项目：外部项目方发布或授权展示的合作需求。
- 入选 / 孵化观察项目：经过初步筛选，进入帧火花观察、孵化或合作洽谈范围的项目。

第一版不建议使用“帧火花推荐项目”这个名称，因为“推荐”带有强背书意味。后续如果使用，必须建立审核标准，例如项目资料完整度、版权声明、项目方身份、开发阶段、合作需求真实性和帧火花审核记录。

## 五、平台核心用户

- 项目方：发布项目需求、查看人才、接收申请、发起联系。
- 影视人才：完善人才档案、展示作品和经历、申请项目、接收合作邀请。
- 帧火花运营方：审核项目、审核人才、管理平台内容、处理举报或纠纷线索。
- 潜在合作方 / 制片方 / 投资方：浏览项目机会、筛选人才、观察项目成熟度与合作可能性。

## 六、核心对象模型

### User 用户

系统登录主体。用于承载账号、权限、联系方式、安全设置和身份状态。

### UserProfile 用户资料

用户的基础资料层。可包含昵称、头像、联系方式、城市、认证信息和公开展示设置。

### ProductionEntity 项目方实体

项目方实体表示真实发起或管理项目的一方，可以是个人、工作室、公司、剧组或制片团队。

User 可以创建或加入多个 ProductionEntity。Project 应归属于 ProductionEntity，而不是直接只归属于某一个 User。这样后续才能表达一个制片团队、多名成员共同管理项目、不同成员拥有不同权限的情况。

ProductionEntity 是区分“账号”和“项目方主体”的关键对象。没有这一层，平台很容易退化成个人用户随意发布项目，后续也难以处理团队权限、项目归属、公司主体、剧组主体和责任边界。

### TalentProfile 人才档案

影视人才的职业档案。用于展示职业身份、技能标签、作品履历、可合作状态和合作偏好。

### Project 项目

项目本体。用于描述项目名称、类型、阶段、来源、标签、公开简介和审核状态。

### ProjectDemand 项目需求 / 招募岗位

项目当前正在寻找的人或合作资源。项目机会页的核心展示对象应是 ProjectDemand，而不是单纯 Project。

### Work 作品 / 履历

用户参与过的作品或可展示成果。可作为人才档案和申请项目的可信支撑。

### WorkCredit 作品贡献关系

WorkCredit 表示一个作品中的具体贡献关系。

一个 Work 可以有多个 TalentProfile 参与，每个人在作品中有不同角色，例如编剧、导演、摄影、演员、剪辑、制片、美术等。不要只用 Work 直接绑定单一用户，否则后期无法表达多人协作作品，也无法建立真实的作品关系图谱。

WorkCredit 的价值在于把“作品”与“具体贡献”拆开：作品是成果，贡献关系才说明某个人在其中做了什么。

### Application 申请 / 投递

人才对某个项目需求发起的申请记录。

### CollaborationRecord 合作记录

CollaborationRecord 表示真实发生过的合作关系，是合作关系图谱的基础。

Endorsement 是评价或背书，CollaborationRecord 是合作事实记录，两者不要混为一谈。平台可以先记录“谁和谁在什么项目中合作过、担任什么角色、合作是否完成”，再在此基础上允许双方或项目方发起背书。

合作记录应尽量避免单方虚构，最好由双方确认或由项目方确认。

### Match 匹配记录

平台、运营方或规则系统产生的人才与项目需求之间的匹配记录。第一版可不做复杂推荐算法，只保留未来扩展空间。

### Endorsement 背书 / 合作评价

用于沉淀合作可信度。第一版建议先做合作记录和文字背书，不急着做公开评分。

### ContactRequest 联系请求

用户之间、项目方与人才之间的轻量联系入口。第一版不做复杂即时聊天，先做联系请求与状态流转。

### ReviewStatus 审核状态

用于项目、需求、人才档案、作品、背书等对象的审核状态控制。

### ActionLog 行为日志

从第一天就应预留 ActionLog。

ActionLog 至少记录：谁、什么时间、对什么对象、做了什么动作。它不一定第一版就做复杂分析，但字段和写入位置要从架构层预留。

ActionLog 的长期价值包括：

- 推荐优化
- 风控
- 反作弊
- 平台运营分析
- 审核追溯
- 纠纷处理时的基础证据

## 七、Project 项目字段建议

Project 建议字段：

- projectId
- productionEntityId
- projectName
- projectType
- sourceType
- developmentStage
- genreTags
- publicSummary
- coverImage
- city
- remoteAllowed
- visibility
- reviewStatus
- createdBy
- createdAt
- updatedAt

字段说明：

- projectType：短片、长片、剧集、网络电影、纪录片、动画、实验影像等。
- productionEntityId：项目所属的项目方实体。Project 归属于 ProductionEntity，不应只直接归属于 User。
- sourceType：framespark_owned、external、selected_observation 等。
- developmentStage：概念、梗概、大纲、剧本开发、筹备、拍摄、后期、发行等。
- visibility：公开、仅审核可见、仅受邀可见、草稿。
- reviewStatus：pending、approved、rejected、hidden / removed 等。

Project 是项目容器，不是直接匹配单元。它承载项目背景、调性、开发阶段、项目来源、所属项目方、公开简介和审核状态。

帧火花自有项目、外部项目、入选 / 孵化观察项目，不应拆成三个独立实体。统一使用 Project 实体，通过 sourceType 字段区分：

- framespark_owned：帧火花自有 / 主控项目
- external：外部项目方发布
- selected_observation：入选 / 孵化观察项目

同时结合 reviewStatus、visibility、ProductionEntity 权限、是否进入首页展示等字段，决定项目展示范围和权限。

外部项目默认不叫“推荐项目”。“推荐 / 入选 / 自有”必须分层，避免平台背书风险。

## 八、ProjectDemand 项目需求字段建议

ProjectDemand 建议字段：

- demandId
- projectId
- roleNeeded
- description
- cooperationType
- budgetRange
- locationRequirement
- availabilityRequirement
- experienceRequirement
- portfolioRequired
- expectedStartDate
- expectedEndDate / expectedDuration
- projectCity
- workMode
- acceptsNonLocalTalent
- providesTravelSupport
- status
- reviewStatus
- createdAt

项目人才生态平台的“项目机会”页面主要展示的其实是 ProjectDemand，而不是单纯 Project。因为用户真正关心的是“这个项目正在找什么人”。

Project 是项目容器。ProjectDemand 是匹配单元。真正进入匹配池的是 ProjectDemand，不是 Project 本身。

示例：

- “某短片项目”不是匹配单元。
- “某短片 7 月上海寻找摄影指导，驻组 5 天，有偿”才是匹配单元。

ProjectDemand 必须依附于 Project 存在，不能脱离项目单独发布。原因是同一项目下的多个需求需要共享项目背景、调性、阶段、团队与来源信息。

字段说明：

- roleNeeded：编剧、导演、制片、摄影、美术、剪辑、演员、宣发、项目顾问等。
- cooperationType：有偿合作、联合开发、项目制、长期合作、志愿 / 低预算、待议。
- budgetRange：可选公开范围，不强制显示具体金额。
- workMode：本地、远程、驻组、混合。
- status：open、paused、filled、closed。
- portfolioRequired：是否需要提交作品集或代表作品。

- city

- availabilityStatus
- availabilityBlocks
- baseCity

- bio

字段说明：

- currentRoles：可多选，如编剧、导演、制片、摄影、剪辑、演员等。
- primaryRole：主要身份，用于列表展示和筛选。
- availableStatus / availabilityStatus：可合作、暂不接活、仅远程、仅长期、仅项目制、档期待确认等。

Work 建议字段：

- workId
- userId
- title
- workType
- roleInWork
- year
- description
- mediaUrl
- poster
- link
- visibility
- reviewStatus

字段说明：

- workType：短片、长片、剧集、广告、MV、纪录片、动画、剧本、摄影作品、剪辑作品等。
- roleInWork：用户在该作品中的职责。

## 十一、申请与联系

第一版不做复杂即时聊天。优先做轻量申请和联系请求：

- Application：人才对项目需求发起申请，包含申请说明、作品链接、状态和项目方处理记录。
- ContactRequest：用户之间发起联系请求，包含发起人、接收人、关联项目或需求、联系理由和处理状态。

建议状态：

- pending：待处理
- accepted：已接受
- declined：已拒绝
- withdrawn：已撤回
- expired：已过期

这样可以先完成合作连接闭环，同时避免即时聊天、消息安全、骚扰控制和通知系统过早复杂化。

## 十二、背书与合作记录

Endorsement 用于建立平台可信度。

第一版可以先做合作记录和文字背书，不急着做公开评分。原因是评分系统容易带来争议、刷分、报复性评价和平台责任边界问题。

建议第一版包括：

- 合作对象
- 关联项目
- 合作角色
- 合作时间
- 背书文字
- 是否公开
- 是否双方确认
- 审核状态

后续可再扩展为更复杂的信用机制，但应避免在早期承诺平台对合作结果进行强担保。

## 审核机制必须前置

上线时必须有人工审核机制，至少覆盖 Project 和 ProjectDemand。

未通过审核的 ProjectDemand 不进入匹配池。项目发布、需求发布、人才档案、作品资料都应有 reviewStatus 字段。

审核状态第一版可以简化为：

- pending：待审核
- approved：已通过
- rejected：已拒绝
- hidden / removed：隐藏或移除

审核不一定第一版就做复杂工作流系统，但 reviewStatus 字段和“未审核不进入匹配池”的规则必须从架构层存在。

## 权限与内容归属

权限不应只按角色判断，而应按“动作 + 对象”判断。

示例：能否编辑 Project，不是看 User 是否是“项目方角色”，而是看 User 是否属于该 Project 所属的 ProductionEntity，且是否拥有对应权限。

内容归属建议：

- Project 归属于 ProductionEntity。
- ProjectDemand 归属于 Project。
- TalentProfile 归属于 User。
- Work 可由人才上传，也可关联 Project。
- WorkCredit 表示人才在作品中的具体贡献。
- Endorsement 归发出方所有，被背书方不能修改，但可选择隐藏或申诉。
- CollaborationRecord 需要双方或项目方确认，避免单方虚构合作。

权限模型应支持一个 User 同时拥有多个身份和多个组织关系，而不是只用一个 role 字段决定所有行为。

## 档期与地域协作匹配

档期和地域协作方式是匹配硬条件。

人才端建议字段：

- availabilityStatus
- availabilityBlocks
- baseCity
- availableCities
- acceptsRemote
- acceptsTravel
- acceptsOnsite
- maxTravelDays
- travelRequirement
- lastAvailabilityUpdatedAt

项目需求端建议字段：

- expectedStartDate
- expectedEndDate / expectedDuration
- projectCity
- workMode：本地 / 远程 / 驻组 / 混合
- acceptsNonLocalTalent
- providesTravelSupport

基础匹配规则：

- 项目必须本地 + 人才不在本地且不接受异地 = 不匹配。
- 项目可远程 + 人才接受远程 = 可匹配。
- 项目需驻组 + 人才接受异地且档期覆盖 = 可匹配。
- 项目周期与人才不可合作区间冲突 = 不推荐或降权。
- 档期长期未更新 = 标记档期待确认。

这些规则是第一版就应保留的硬约束。即使暂时不做复杂算法，也不能忽略档期、城市、远程、驻组和差旅条件。

## 推荐原因标签

第一版的推荐原因不是复杂 AI 推荐算法。

第一版的推荐原因应来自硬条件和基础软条件的命中项展示。用标签解释“为什么推荐”，比一个不透明分数更可信。

示例标签：

- 工种对应
- 档期可用
- 城市匹配
- 可远程
- 可驻组
- 合作方式匹配
- 作品类型接近
- 档期待确认
- 报酬需确认

不要在第一版使用不透明的“匹配度 92%”作为主要表达。可以后续内部计算排序分，但用户可见层应优先展示可理解的推荐原因标签。

## 身份视角

一个 User 可以同时是人才、项目方、创作者、ProductionEntity 成员。

身份不是单一字段，而是场景和动作。前端可以提供当前视角：

- 创作者视角：看适合自己的项目机会。
- 项目方视角：看适合某个 ProjectDemand 的人才。
- 运营视角：审核和治理。

推荐人才不应作为所有用户的默认模块。只有项目方视角或找人场景才展示推荐人才。

这一点非常重要：如果所有用户默认看到“推荐人才”，页面会更像人才库；如果项目方围绕某个需求看候选人，平台才会更接近“项目需求驱动的匹配工作台”。

## 十三、综合页结构

项目人才生态平台首页应包括：

- 顶部搜索区
- 搜项目
- 搜人才
- 发布项目需求
- 完善人才档案
- 项目机会区
- 推荐人才区
- 职业分类入口
- 最新项目需求
- 最新加入人才
- 平台可信机制说明

页面重点不应做成品牌介绍页，而应直接进入“找项目 / 找人才 / 发需求 / 建档案”的使用场景。

## 十四、项目详情页

项目详情页建议包括：

- 项目名称
- 项目类型
- 开发阶段
- 项目来源
- 公开简介
- 项目标签
- 城市 / 远程
- 当前招募需求
- 项目方信息
- 审核状态
- 申请参与按钮
- 相关推荐人才

注意：

项目详情页展示 Project，但用户行动重点通常落在 ProjectDemand 上。因此“当前招募需求”应是页面核心区域之一。

## 十五、人才详情页

人才详情页建议包括：

- 姓名 / 昵称
- 当前主身份
- 职业标签
- 城市 / 可合作状态
- 个人简介
- 代表作品
- 项目经历
- 技能标签
- 类型偏好
- 合作背书
- 联系 / 邀请合作按钮
- 相关推荐项目

人才详情页应服务两个目标：

- 让项目方快速判断此人是否适合当前项目。
- 让人才通过作品、经历和背书建立可信度。

## 十六、官网版与小程序版分工

当前阶段优先设计和开发 Web 端核心闭环。小程序第一阶段不开发。

官网 Web 版适合：

- 完善详细档案
- 上传作品集
- 发布项目需求
- 管理项目
- 筛选人才
- 查看完整项目详情
- 申请与联系管理
- 项目方候选人才筛选
- 基础审核后台

小程序版适合：

- 浏览项目机会
- 浏览人才名片
- 收藏
- 申请参与
- 接收通知
- 扫码展示个人主页
- 快速联系
- 档期状态轻量更新

两端必须共用同一套后端，不要各做一套数据。Web 和小程序可以有不同界面，但对象模型、审核状态、用户权限和项目需求数据应保持一致。

Web 是工作台，小程序未来是入口和状态机。微信登录打通属于账号体系架构，不是轻量功能，后续应单独设计。

## 十七、与故事开发诊断系统的关系

两者互相导流，但不混成一个系统。

诊断系统可以在报告底部引导用户进入项目人才生态平台寻找合作方，例如：

- 寻找编剧顾问
- 寻找导演或制片合作
- 发布项目开发需求
- 完善人才档案并参与项目

但第一版不要自动把用户材料公开到项目人才平台。故事材料、诊断报告或项目信息进入项目人才生态平台，必须由用户主动选择，并经过审核。

## 十八、与帧火花自有项目展示的关系

首页“帧火花开发中项目”只展示公司自有或主控项目。

外部项目进入项目人才生态平台的项目机会区。

不要混淆：

- 自有项目
- 外部项目
- 入选 / 孵化观察项目

这三类项目的展示位置、标识、审核标准和平台背书强度都应不同。

## 十九、第一版策略：完整架构下的核心闭环版本

第一版不追求简陋 MVP，而是“完整架构下的核心闭环版本”。

这意味着：数据模型、权限归属、审核状态、行为日志、档期地域字段等底层结构要从一开始预留完整；但外显功能可以只开放核心闭环，不一次性开发所有高级模块。

Web 第一阶段优先做：

- User / TalentProfile
- ProductionEntity
- Project
- ProjectDemand
- Work / WorkCredit
- Availability 轻量字段
- Application / ContactRequest
- ReviewStatus
- ActionLog
- 基础审核后台
- 创作者视角项目机会
- 项目方视角候选人才

后置：

- 小程序
- 微信登录打通
- 即时聊天
- 合同
- 支付
- 公开评分
- 复杂 AI 推荐
- 完整日历
- 信用分体系
- 自动匹配算法高级版

第一版的目标是验证项目方和人才之间是否能形成真实连接，同时确保后续能平滑扩展成双向动态匹配系统。

## 二十、风险与边界

主要风险：

- 外部项目真实性风险
- 版权归属风险
- 虚假招募风险
- 人才资料造假
- 平台背书边界不清
- 项目方与人才合作纠纷
- 双边平台冷启动风险

应对原则：

- 外部项目必须标注来源
- 外部项目默认不叫推荐
- 项目需求发布需要审核
- 人才资料和作品需要审核
- 平台只提供展示与连接，不直接保证合作结果
- 推荐 / 入选 / 自有项目要分层

平台文案应避免过度承诺。尤其是“推荐”“认证”“背书”“入选”等词，需要有明确规则支撑后再使用。

### 冷启动风险

双边平台最大的风险是冷启动。

项目方没有人才会离开，人才没有项目也会离开。上线前必须准备种子项目方、种子 ProjectDemand、种子 TalentProfile，否则平台会空转。

信用机制依赖真实合作记录。冷启动期 CollaborationRecord 和 Endorsement 会很少，因此第一版不能过度依赖信用分。早期更重要的是：

- 资料完整度
- 审核状态
- 作品资料
- 项目来源标注
- 档期和协作方式是否清楚
- 项目需求是否真实具体

## 二十一、后续推进顺序

建议推进顺序：

1. 第一阶段：完成架构文档
2. 第二阶段：设计 Web 核心闭环和身份视角工作台
3. 第三阶段：设计 User / ProductionEntity / TalentProfile / ProjectDemand 数据模型
4. 第四阶段：设计 Web 版项目机会、候选人才、申请联系和审核后台页面
5. 第五阶段：统一后端用户系统、权限、审核状态和 ActionLog
6. 第六阶段：接入项目招募、申请、联系、收藏、通知
7. 第七阶段：接入作品贡献、合作记录和背书
8. 第八阶段：后期再设计小程序、微信登录打通、复杂推荐、信用分和完整项目档案

每一阶段都应围绕核心闭环验证推进，不应把长期愿景直接当成一次性开发清单。

## 当前 talent 静态页的改造方向

当前 talent/index.html 原型偏展示页，不应作为最终形态继续扩展。

下一版应改为身份视角驱动的匹配工作台：

- 游客视角：平台说明 + 选择身份。
- 创作者视角：适合你的项目机会。
- 项目方视角：某个需求的候选人才。
- 运营视角：审核和治理。

推荐人才只应在项目方视角或找人场景出现，不应作为所有用户的默认模块。

页面应提高信息密度，减少长卷轴式展示和大面积空白。平台的核心不是展示“有很多项目和人才”，而是围绕 ProjectDemand 与 TalentProfile 建立可解释、可审核、可追踪的动态匹配关系。
