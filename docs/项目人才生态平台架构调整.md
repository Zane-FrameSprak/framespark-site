# 项目人才生态平台架构调整

本文档用于定义项目人才生态平台的产品方向、信息架构和长期模块边界，不代表所有功能需要一次性开发。正式开发时应按 MVP 优先级拆分实施，并根据实际业务验证结果持续调整。

## 一、背景

帧火花官网目前有三个主要入口：

- 故事开发诊断系统
- 项目人才生态平台
- 帧火花开发中项目

原人才平台更偏人才库，主要围绕人才档案、职业信息和合作记录展开。随着官网产品方向扩展，平台需要升级为“项目 + 人才 + 合作需求”的综合生态平台，既能让项目方发布需求，也能让人才展示能力、寻找项目机会，并为后续合作记录、背书机制和项目孵化提供基础。

## 二、新定位

名称暂定：

帧火花项目人才生态平台

对外可使用：

- 项目人才专区
- 项目招募专区

一句话定位：

项目找人，人找项目，平台提供展示、筛选、连接和基础可信机制。

平台不是单纯人才库，也不是公开项目广场，而是围绕影视项目合作建立的连接入口。第一版应优先解决“谁在找人”“谁能参与”“如何可信地发起联系”这三个问题。

## 三、三个官网入口的边界

### 故事开发诊断系统

故事材料诊断入口。面向一句话创意、故事概念、梗概、大纲、人物小传、世界观设定、片段文本和完整剧本，帮助用户判断材料当前阶段是否成立，以及下一步应补什么。

### 项目人才生态平台

项目与人才连接入口。面向项目方、影视人才、潜在合作方和帧火花运营方，提供项目需求发布、人才档案展示、申请参与、联系请求、合作记录和基础审核。

### 帧火花开发中项目

公司自有项目展示入口。只展示帧火花自有、主控或明确由帧火花参与开发的项目。

帧火花自有项目展示不等于外部项目广场。外部项目应进入项目人才生态平台，不应混进“帧火花开发中项目”。

## 四、项目类型分层

平台内项目至少分为三层：

- 帧火花自有项目：由帧火花主控、开发或明确参与运营的项目。
- 外部合作项目：外部项目方发布或授权展示的合作需求。
- 入选 / 孵化观察项目：经过初步筛选，进入帧火花观察、孵化或合作洽谈范围的项目。

第一版不建议使用“帧火花推荐项目”这个名称，因为“推荐”带有强背书意味。后续如果使用，必须建立审核标准，例如项目资料完整度、版权声明、项目方身份、开发阶段、合作需求真实性和帧火花审核记录。

## 五、平台核心用户

- 项目方：发布项目需求、查看人才、接收申请、发起联系。
- 影视人才：完善人才档案、展示作品和经历、申请项目、接收合作邀请。
- 帧火花运营方：审核项目、审核人才、管理平台内容、处理举报或纠纷线索。
- 潜在合作方 / 制片方 / 投资方：浏览项目机会、筛选人才、观察项目成熟度与合作可能性。

## 六、核心对象模型

### User 用户

系统登录主体。用于承载账号、权限、联系方式、安全设置和身份状态。

### UserProfile 用户资料

用户的基础资料层。可包含昵称、头像、联系方式、城市、认证信息和公开展示设置。

### TalentProfile 人才档案

影视人才的职业档案。用于展示职业身份、技能标签、作品履历、可合作状态和合作偏好。

### Project 项目

项目本体。用于描述项目名称、类型、阶段、来源、标签、公开简介和审核状态。

### ProjectDemand 项目需求 / 招募岗位

项目当前正在寻找的人或合作资源。项目机会页的核心展示对象应是 ProjectDemand，而不是单纯 Project。

### Work 作品 / 履历

用户参与过的作品或可展示成果。可作为人才档案和申请项目的可信支撑。

### Application 申请 / 投递

人才对某个项目需求发起的申请记录。

### Match 匹配记录

平台、运营方或规则系统产生的人才与项目需求之间的匹配记录。第一版可不做复杂推荐算法，只保留未来扩展空间。

### Endorsement 背书 / 合作评价

用于沉淀合作可信度。第一版建议先做合作记录和文字背书，不急着做公开评分。

### ContactRequest 联系请求

用户之间、项目方与人才之间的轻量联系入口。第一版不做复杂即时聊天，先做联系请求与状态流转。

### ReviewStatus 审核状态

用于项目、需求、人才档案、作品、背书等对象的审核状态控制。

## 七、Project 项目字段建议

Project 建议字段：

- projectId
- projectName
- projectType
- sourceType
- developmentStage
- genreTags
- publicSummary
- coverImage
- city
- remoteAllowed
- visibility
- reviewStatus
- createdBy
- createdAt
- updatedAt

字段说明：

- projectType：短片、长片、剧集、网络电影、纪录片、动画、实验影像等。
- sourceType：framespark_owned、external_cooperation、incubation_watch 等。
- developmentStage：概念、梗概、大纲、剧本开发、筹备、拍摄、后期、发行等。
- visibility：公开、仅审核可见、仅受邀可见、草稿。
- reviewStatus：draft、pending、approved、rejected、archived 等。

## 八、ProjectDemand 项目需求字段建议

ProjectDemand 建议字段：

- demandId
- projectId
- roleNeeded
- description
- cooperationType
- budgetRange
- locationRequirement
- availabilityRequirement
- experienceRequirement
- portfolioRequired
- status
- reviewStatus
- createdAt

项目人才生态平台的“项目机会”页面主要展示的其实是 ProjectDemand，而不是单纯 Project。因为用户真正关心的是“这个项目正在找什么人”。

字段说明：

- roleNeeded：编剧、导演、制片、摄影、美术、剪辑、演员、宣发、项目顾问等。
- cooperationType：有偿合作、联合开发、项目制、长期合作、志愿 / 低预算、待议。
- budgetRange：可选公开范围，不强制显示具体金额。
- status：open、paused、filled、closed。
- portfolioRequired：是否需要提交作品集或代表作品。

## 九、TalentProfile 人才档案字段建议

TalentProfile 建议字段：

- talentId
- userId
- displayName
- currentRoles
- primaryRole
- city
- availableStatus
- bio
- skillTags
- genrePreference
- workExperience
- portfolioLinks
- representativeWorks
- verificationStatus
- reviewStatus
- createdAt
- updatedAt

字段说明：

- currentRoles：可多选，如编剧、导演、制片、摄影、剪辑、演员等。
- primaryRole：主要身份，用于列表展示和筛选。
- availableStatus：可合作、暂不接活、仅远程、仅长期、仅项目制等。
- verificationStatus：未认证、基础认证、作品认证、合作记录认证。
- representativeWorks：可关联 Work，也可第一版保存为轻量文本或链接。

## 十、Work 作品字段建议

Work 建议字段：

- workId
- userId
- title
- workType
- roleInWork
- year
- description
- mediaUrl
- poster
- link
- visibility
- reviewStatus

字段说明：

- workType：短片、长片、剧集、广告、MV、纪录片、动画、剧本、摄影作品、剪辑作品等。
- roleInWork：用户在该作品中的职责。
- visibility：公开、仅审核可见、仅自己可见。
- reviewStatus：作品是否通过平台展示审核。

## 十一、申请与联系

第一版不做复杂即时聊天。优先做轻量申请和联系请求：

- Application：人才对项目需求发起申请，包含申请说明、作品链接、状态和项目方处理记录。
- ContactRequest：用户之间发起联系请求，包含发起人、接收人、关联项目或需求、联系理由和处理状态。

建议状态：

- pending：待处理
- accepted：已接受
- declined：已拒绝
- withdrawn：已撤回
- expired：已过期

这样可以先完成合作连接闭环，同时避免即时聊天、消息安全、骚扰控制和通知系统过早复杂化。

## 十二、背书与合作记录

Endorsement 用于建立平台可信度。

第一版可以先做合作记录和文字背书，不急着做公开评分。原因是评分系统容易带来争议、刷分、报复性评价和平台责任边界问题。

建议第一版包括：

- 合作对象
- 关联项目
- 合作角色
- 合作时间
- 背书文字
- 是否公开
- 是否双方确认
- 审核状态

后续可再扩展为更复杂的信用机制，但应避免在早期承诺平台对合作结果进行强担保。

## 十三、综合页结构

项目人才生态平台首页应包括：

- 顶部搜索区
- 搜项目
- 搜人才
- 发布项目需求
- 完善人才档案
- 项目机会区
- 推荐人才区
- 职业分类入口
- 最新项目需求
- 最新加入人才
- 平台可信机制说明

页面重点不应做成品牌介绍页，而应直接进入“找项目 / 找人才 / 发需求 / 建档案”的使用场景。

## 十四、项目详情页

项目详情页建议包括：

- 项目名称
- 项目类型
- 开发阶段
- 项目来源
- 公开简介
- 项目标签
- 城市 / 远程
- 当前招募需求
- 项目方信息
- 审核状态
- 申请参与按钮
- 相关推荐人才

注意：

项目详情页展示 Project，但用户行动重点通常落在 ProjectDemand 上。因此“当前招募需求”应是页面核心区域之一。

## 十五、人才详情页

人才详情页建议包括：

- 姓名 / 昵称
- 当前主身份
- 职业标签
- 城市 / 可合作状态
- 个人简介
- 代表作品
- 项目经历
- 技能标签
- 类型偏好
- 合作背书
- 联系 / 邀请合作按钮
- 相关推荐项目

人才详情页应服务两个目标：

- 让项目方快速判断此人是否适合当前项目。
- 让人才通过作品、经历和背书建立可信度。

## 十六、官网版与小程序版分工

官网 Web 版适合：

- 完善详细档案
- 上传作品集
- 发布项目需求
- 管理项目
- 筛选人才
- 查看完整项目详情

小程序版适合：

- 浏览项目机会
- 浏览人才名片
- 收藏
- 申请参与
- 接收通知
- 扫码展示个人主页
- 快速联系

两端必须共用同一套后端，不要各做一套数据。Web 和小程序可以有不同界面，但对象模型、审核状态、用户权限和项目需求数据应保持一致。

## 十七、与故事开发诊断系统的关系

两者互相导流，但不混成一个系统。

诊断系统可以在报告底部引导用户进入项目人才生态平台寻找合作方，例如：

- 寻找编剧顾问
- 寻找导演或制片合作
- 发布项目开发需求
- 完善人才档案并参与项目

但第一版不要自动把用户材料公开到项目人才平台。故事材料、诊断报告或项目信息进入项目人才生态平台，必须由用户主动选择，并经过审核。

## 十八、与帧火花自有项目展示的关系

首页“帧火花开发中项目”只展示公司自有或主控项目。

外部项目进入项目人才生态平台的项目机会区。

不要混淆：

- 自有项目
- 外部项目
- 入选 / 孵化观察项目

这三类项目的展示位置、标识、审核标准和平台背书强度都应不同。

## 十九、第一版 MVP 范围

建议第一版只做：

- 项目人才综合首页
- 人才列表
- 人才详情
- 项目机会列表
- 项目详情
- 发布项目需求
- 完善人才档案
- 申请参与 / 发起联系
- 基础审核状态

暂不做：

- 即时聊天
- 合同
- 支付
- 复杂推荐算法
- 多文件项目档案
- 自动匹配系统
- 公开评分系统
- 项目融资

第一版的目标是验证项目方和人才之间是否能形成真实连接，而不是一次性搭建完整行业平台。

## 二十、风险与边界

主要风险：

- 外部项目真实性风险
- 版权归属风险
- 虚假招募风险
- 人才资料造假
- 平台背书边界不清
- 项目方与人才合作纠纷

应对原则：

- 外部项目必须标注来源
- 外部项目默认不叫推荐
- 项目需求发布需要审核
- 人才资料和作品需要审核
- 平台只提供展示与连接，不直接保证合作结果
- 推荐 / 入选 / 自有项目要分层

平台文案应避免过度承诺。尤其是“推荐”“认证”“背书”“入选”等词，需要有明确规则支撑后再使用。

## 二十一、后续推进顺序

建议推进顺序：

1. 第一阶段：完成架构文档
2. 第二阶段：设计项目人才综合页原型
3. 第三阶段：设计人才档案和项目需求数据模型
4. 第四阶段：设计 Web 版人才平台页面
5. 第五阶段：设计小程序人才平台页面
6. 第六阶段：统一后端用户系统和权限
7. 第七阶段：接入项目招募、申请、收藏、通知
8. 第八阶段：后期再接匹配、背书、项目档案

每一阶段都应以 MVP 验证为准，不应把长期愿景直接当成一次性开发清单。
